# CIPH v0.20 Evaluator Replay Readiness Design

## Goal

Make evaluator runs replay-ready without executing external evaluators by default. v0.18 identified score producers and v0.19 made their artifacts tamper-evident; v0.20 should record enough local metadata to preflight whether an evaluator could be replayed later.

## Options Considered

1. Add a metadata-only `replay` object to evaluator manifests and validate it with a standalone script.
   This is the selected approach. It records command argv, working directory, environment allowlist, local-only effect policy, and expected output hashes without adding an execution engine or provider calls.

2. Execute evaluator commands in closeout.
   This is too early. It would introduce subprocess safety, timeouts, external effects, and provider credentials before the harness has a replay policy.

3. Store replay instructions only in notes.
   Notes are easy to write but cannot be validated mechanically or compared to integrity hashes.

## Contract

Evaluator manifests may include:

```json
"replay": {
  "schema_version": "ciph.evaluator-replay.v1",
  "mode": "metadata-only",
  "working_directory": ".",
  "command_metadata": {
    "argv": ["python3", "tools/evaluate.py", "--phase", "search"],
    "shell": false
  },
  "env_allowlist": ["PATH", "PYTHONPATH"],
  "external_effect_policy": "local-only",
  "expected_output_hashes": {
    "runs/my-run/candidates/frontier/score.json": "sha256:<hex>"
  }
}
```

`scripts/validate_evaluator_replay.py` follows `EVALUATION.json`, loads score provenance, then validates each referenced evaluator manifest. It checks replay shape, local working directory safety, argv command metadata, unique environment allowlist entries, local-only policy, output digest coverage, digest format, current output bytes, and agreement with `integrity.output_hashes` when integrity is present.

## Non-Goals

- No evaluator execution.
- No provider API calls.
- No environment value capture.
- No secrets or credentials in manifests.
- No retroactive migration of historical runs.

## Testing

Use TDD for valid search/holdout replay metadata, missing replay object, unsafe working directory, shell execution, empty env names, output hash mismatch, integrity disagreement, and CLI HTML output. Dogfood must include search and holdout replay contracts plus a generated replay readiness report.
