# CIPH v0.16 Holdout Release Gate Design

## Goal

Add a deterministic command that transitions an evaluation protocol from `search` to `holdout_released` only when the run is ready to expose holdout evaluation.

## Gate Rules

The release gate reads `runs/<run-id>/EVALUATION.json` and refuses to mutate it unless:

- Current phase is `search`, or it is already released and internally valid.
- `validate_evaluation.py` passes in the current search state.
- `frontier_candidate_ids` is non-empty and every frontier candidate is listed.
- The number of prior `holdout_releases` is below `budget.max_holdout_releases`.
- Every frontier candidate passes `validate_candidate.py`.
- No search-phase candidate exposes `holdout_scores` or `holdout_score_path`.

## Transition

On release, the command writes:

- `phase: "holdout_released"`
- `holdout_set.sealed: false`
- a new `holdout_releases[]` entry with release index, timestamp, and frontier IDs

The command is intentionally idempotent after release: an already released valid protocol reports success without appending another release. That keeps manifest checks repeatable.

## Non-Goals

- No automatic scenario execution.
- No holdout score generation.
- No encrypted holdout payload store.
- No model/provider integration.

## Success Criteria

- `scripts/release_holdout.py` enforces the gate and renders a report.
- `scripts/validate_evaluation.py` accepts valid released protocols and rejects malformed release state.
- Dogfood v0.16 demonstrates the transition and keeps holdout scores absent.
- Bundled and installed Proofline assets expose the release command.
