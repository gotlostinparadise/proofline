# CIPH v0.18 Score Provenance Design

## Goal

Make scores auditable. Every research-grade search or holdout score should point to the evaluator manifest, command, inputs, outputs, and evidence that produced it.

## Options Considered

1. Add a standalone provenance validator and optional score fields.
   This keeps historical runs valid, lets new research-grade runs opt into strict provenance, and makes the contract explicit in manifests. This is the selected approach.

2. Make provenance mandatory in `validate_candidate.py` and `validate_evaluation.py`.
   This is stricter, but it would force migration of every historical run and make repo closeout noisy.

3. Store provenance only in run-level notes.
   This is easy to write, but scripts cannot prove the link from a score to the command and evidence that generated it.

## Contract

Evaluator manifests live under `runs/<run-id>/evaluators/<evaluator-id>.json` with schema `ciph.evaluator-manifest.v1`. Required fields are `evaluator_id`, `evaluation_phase`, `command`, `input_paths`, `output_paths`, `evidence_paths`, and `metric_keys`.

Score records may include:

```json
"score_provenance": {
  "schema_version": "ciph.score-provenance.v1",
  "evaluator_id": "search-evaluator",
  "evaluator_manifest_path": "runs/my-run/evaluators/search-evaluator.json",
  "evaluation_phase": "search",
  "produced_at": "2026-05-20T07:00:00Z",
  "input_paths": ["runs/my-run/candidates/frontier/source/README.md"],
  "evidence_paths": ["runs/my-run/artifacts/search-evidence.txt"]
}
```

The new `scripts/validate_score_provenance.py` validates candidate `score.json` records and released holdout score records listed in `EVALUATION.json`. It checks provenance shape, evaluator manifest shape, phase agreement, local path existence, score output linkage, and evidence paths.

## Reporting

`candidate_summary.py` and `final_comparison.py` surface evaluator IDs when provenance is present. They do not fail if provenance is absent; strictness belongs to `validate_score_provenance.py` so historical reports stay readable.

## Non-Goals

- No benchmark execution engine.
- No provider API calls.
- No cryptographic signing.
- No retroactive migration of historical score files.

## Testing

Use TDD for the validator and report columns. Dogfood must include search and holdout evaluator manifests, score provenance in both score types, generated evidence files, a provenance report, and the normal repo gate.
