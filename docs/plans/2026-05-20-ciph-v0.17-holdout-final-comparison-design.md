# CIPH v0.17 Holdout Final Comparison Design

## Goal

Add the post-release half of the research loop: ingest externally produced holdout scores only after the holdout gate has released, validate those scores as first-class protocol records, and render a final comparison report that separates search performance from holdout performance.

## Options Considered

1. Separate holdout score files referenced from `EVALUATION.json`.
   This keeps search candidate scores immutable, makes ingestion auditable, and lets validation reason over explicit score paths. This is the selected approach.

2. Append `holdout_scores` directly into each candidate `score.json`.
   This is compact, but it weakens the search/holdout boundary and makes it harder to prove the search record was not rewritten.

3. Generate an external final report without mutating `EVALUATION.json`.
   This avoids protocol changes, but leaves no durable link between the released frontier and the score file used for final comparison.

## Protocol

Holdout score files live at `runs/<run-id>/holdout_scores/<candidate-id>.json` and use schema version `ciph.holdout-score.v1`. Required fields are `candidate_id`, `release_index`, `scored_at`, `scenario_ids`, and `holdout_scores`. The score object uses the same objective metric keys as search scoring: `task_success`, `audit_completeness`, `cost_tokens`, `wall_minutes`, and `defect_escape_rate`.

`scripts/ingest_holdout_scores.py` accepts an incoming score JSON file, verifies that the run is already `holdout_released`, verifies the candidate was part of the matching release frontier, writes the canonical score file, and updates that candidate record in `EVALUATION.json` with `evaluation_phase: "holdout"` and `holdout_score_path`.

`scripts/validate_evaluation.py` remains the protocol validator. During `search`, it continues to forbid holdout score paths. During `holdout_released`, it validates any declared holdout score path, candidate ID, release index, scenario IDs, and numeric metric shape.

## Reporting

`scripts/final_comparison.py` reads `EVALUATION.json`, candidate search scores, and ingested holdout scores. It emits an HTML or text report showing search metrics, holdout metrics, generalization delta, and final status. The final winner is the candidate with the highest holdout `task_success`; ties are deterministic by candidate ID.

## Non-Goals

- No scenario runner or model evaluation engine.
- No hidden holdout payload storage.
- No automatic benchmark execution.
- No provider integration.

## Testing

The implementation uses TDD around ingestion, validation, reporting, CLI execution, and Proofline bundle installation. The dogfood run must release holdout, ingest a score, produce final comparison, run manifest checks, and pass the repository gate.
