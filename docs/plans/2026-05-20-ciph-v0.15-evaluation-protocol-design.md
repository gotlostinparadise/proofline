# CIPH v0.15 Evaluation Protocol Design

## Goal

Add deterministic search-set versus holdout discipline to CIPH research runs without adding a model runner or benchmark executor.

## Choice

Use an explicit `EVALUATION.json` file at the run root. The file records the baseline candidate, fixed search and holdout scenario IDs, budget limits, current phase, candidate score paths, and selected frontier candidates. A validator enforces the protocol and renders evidence.

## Protocol Shape

```json
{
  "schema_version": "ciph.evaluation.v1",
  "run_id": "my-run",
  "phase": "search",
  "baseline_candidate_id": "baseline",
  "search_set": {"scenario_ids": ["s1", "s2"]},
  "holdout_set": {"scenario_ids": ["h1"], "sealed": true},
  "budget": {"max_candidates": 3, "max_holdout_releases": 1},
  "frontier_candidate_ids": [],
  "candidates": [
    {
      "candidate_id": "baseline",
      "role": "baseline",
      "evaluation_phase": "search",
      "score_path": "runs/my-run/candidates/baseline/score.json"
    }
  ]
}
```

## Rules

- Search and holdout scenario IDs must be non-empty and disjoint.
- The baseline candidate must exist and be listed as a candidate.
- Search phase forbids holdout score paths and candidate score files containing `holdout_scores`.
- Holdout release requires at least one selected frontier candidate.
- Budgets must be fixed with positive integer limits.
- Candidate score paths must exist and match their candidate IDs.

## Non-Goals

- No scenario execution.
- No automatic frontier selection.
- No hidden encrypted holdout store.
- No provider API integration.

## Success Criteria

- `scripts/validate_evaluation.py` validates and reports the protocol.
- Candidate summaries show evaluation phase and holdout status when `EVALUATION.json` exists.
- Dogfood run includes a valid protocol and generated evaluation report.
- Bundled and installed Proofline assets expose the same workflow.
