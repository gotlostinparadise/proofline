Research synthesis and proposed architecture

Agent Harness for Complex Coding Projects

A practical harness design that combines searchable execution history, natural-language contracts, delegated workspaces, and evaluator-aligned verification for long-running coding work.

Meta-Harness: End-to-End Optimization of Model Harnesses Lee, Nair, Zhang, Lee, Khattab, Finn. arXiv:2603.28052v1. Natural-Language Agent Harnesses Pan, Zou, Guo, Ni, Zheng. arXiv:2603.25723.

Core Thesis

Complex coding projects need more than a better prompt. They need a harness: the layer that decides what state persists, which context is visible, how work is delegated, what artifacts must be produced, how failures are classified, and which evidence is strong enough to stop.

State

Filesystem-backed memory beats lossy summaries

The Meta-Harness paper shows that optimization improves when the proposer can inspect prior source code, scores, prompts, tool calls, outputs, and state updates through normal file operations instead of relying only on scalar scores or compressed feedback.

Contracts

Natural language is useful when bounded

The NLAH paper argues that harness logic can be represented as structured text if deterministic scripts and adapters carry hard checks such as tests, linters, scrapers, verifiers, manifests, and final artifact validation.

Verification

More process is not automatically better

Ablations in NLAH show that extra stages can improve auditability while still harming task outcomes when local acceptance diverges from the final evaluator. The harness must stay aligned with the actual acceptance object.

Research Takeaways

The two papers point to complementary design rules: Meta-Harness focuses on optimizing harness code from rich prior experience; NLAH focuses on making harness logic portable, inspectable, executable, and ablatable as structured natural language.

Finding Evidence from papers Design implication for coding projects
Harnesses are executable context systems They determine what is stored, retrieved, and shown to the model; small changes can produce large performance gaps. Represent prompts, memory, retrieval, delegation, tool policy, and verification as one governed system.
Full traces matter for credit assignment Meta-Harness stores every evaluated candidate with code, scores, and execution traces in a growing filesystem. Every run should leave searchable logs, decisions, failed attempts, commands, outputs, and artifacts.
The proposer should inspect selectively Meta-Harness relies on a coding agent using shell-style inspection instead of stuffing all history into context. Give agents path-addressable state plus query tools; keep context assembly explicit and inspectable.
Harness logic can be text if contracts are hard NLAH defines roles, stages, adapters, scripts, state semantics, failure taxonomy, retry rules, and stop rules. Use natural-language harness specs for orchestration, backed by deterministic scripts for gates.
Delegation needs visible boundaries NLAH separates a runtime-owned parent from child agents with explicit task packets and output paths. Use child workspaces with precise responsibilities, budgets, permissions, and normalized responses.
Evaluator alignment dominates process polish NLAH reports cases where local revalidation succeeded but the official evaluator still failed. Final gates must test the real success condition, not only local proxies or narrative confidence.

Invented Harness: CIPH

CIPH, the Complex Implementation Project Harness, is a repo-native harness for hard coding tasks. It turns a vague project objective into a governed sequence of inspectable contracts, delegated execution, evidence promotion, and completion audit.

1. Intake Parse the objective, repo rules, facts that need MCP or documentation, permissions, and hard deliverables.
2. Scope Build a prompt-to-artifact checklist and identify source-of-truth files, tests, and external docs.
3. Design Produce a bounded plan with contracts, roles, allowed write sets, failure taxonomy, and stop gates.
4. Execute Run parent orchestration plus child workspaces for independent subtasks; log every material action.
5. Verify Run evaluator-aligned checks, inspect artifacts, and record command output as evidence.
6. Close Compare objective against evidence, classify gaps, and only then report complete or continue.

Harness Specification

Runtime charter

  • The parent agent owns orchestration, scope control, evidence promotion, and final audit.
  • Substantive implementation may run in child workspaces only when tasks are independent and bounded.
  • Facts about APIs, config keys, CLI flags, pricing, limits, schemas, or product behavior require authoritative documentation before setup steps or code changes.
  • Secrets are never printed; logs are redacted before being promoted into artifacts.
  • Completion claims require fresh verification evidence mapped back to the original objective.

Harness skill

  • Define role prompts for planner, implementer, reviewer, verifier, and closeout auditor.
  • Define stage transitions: plan, implement, local verify, independent review, repair, closeout.
  • Define adapters: test runner, docs fetcher, static checker, browser driver, log redactor, artifact manifest checker.
  • Define failure taxonomy: missing fact, stale fact, bad patch, failing verifier, evaluator mismatch, incomplete artifact, unsafe scope expansion.
  • Define retry rules: repair only the failing contract; escalate when the acceptance object itself is unclear.

Canonical Workspace

The harness is file-backed so it survives context compaction, enables selective inspection, and makes delegation boundaries auditable.

Contracts

Task contract

Required outputs, forbidden changes, target files, facts to verify, budget, and acceptance object.

Child contract

Role, owned write set, inputs, permissions, completion condition, output path, and failure reporting format.

Artifact contract

Exact files that must exist, schema or format requirements, checks that validate them, and evidence pointers.

Fact contract

Volatile claims require a cited source, access date, authority ranking, and local applicability decision.

Verification contract

Every completion claim maps to a command, inspected file, browser trace, or explicit gap record.

Stop contract

The run stops only when every deliverable is covered by evidence or the blocker is made concrete.

Decision Model

CIPH keeps heavy orchestration optional. The harness should add structure only when it reduces uncertainty or improves evaluator alignment.

Condition Harness behavior Reasoning
Small local bug with clear tests Use one direct implementer loop plus verification. Heavy candidate search can add cost without improving a tight repair path.
Ambiguous architecture or multiple subsystems Require design, artifact contracts, and independent review before implementation. The main risk is committing to the wrong boundary, not typing the patch.
Independent slices with disjoint files Spawn child workspaces with isolated write ownership and normalized responses. Parallelism helps only when outputs can be integrated without hidden coupling.
Volatile external API or product behavior Consult authoritative MCP or vendor docs before setup steps or code. Harness quality depends on preventing plausible but stale details from entering the plan.
Final evaluator differs from local proxy Promote evaluator alignment to a blocking risk and adjust gates. NLAH case studies show local acceptance can be misleading when it is not the actual judge.

Optimization Loop

The harness can improve itself using a Meta-Harness style outer loop. Each candidate harness is evaluated on a search set, then all artifacts and traces are stored for later selective inspection.

Candidate record

{
  "candidate_id": "ciph-017",
  "parent_ids": ["ciph-011", "ciph-014"],
  "changed_modules": ["verification", "delegation"],
  "search_scores": {
    "task_success": 0.76,
    "cost_tokens": 1240000,
    "wall_minutes": 31,
    "audit_completeness": 0.94
  },
  "trace_paths": [
    "candidates/017/trace/prompts.jsonl",
    "candidates/017/trace/tools.jsonl",
    "candidates/017/trace/failures.md"
  ],
  "pareto_status": "frontier"
}

Search policy

  • Keep a Pareto frontier over success, cost, time, auditability, and defect escape rate.
  • Let the proposer inspect any prior candidate, not only the highest scorer.
  • Require leakage audits for benchmark-specific strings or task memorization.
  • Prefer additive changes until trace evidence justifies broad rewrites.
  • Record failed hypotheses, because they are high-value context for future diagnosis.

Verification Matrix

Completion is a checklist over concrete evidence, not a feeling that the implementation looks done.

Claim Required evidence Status rule
Implementation matches objective Prompt-to-artifact checklist maps every explicit requirement to a file, command, or inspected output. Pass only if no objective item is uncovered.
Code works Fresh test, build, lint, typecheck, or runtime command aligned with the acceptance object. Weak if command is a proxy; fail if not run.
External facts are correct Authoritative docs consulted, source recorded, and applicability decision noted. Pass only with current source evidence.
Delegated work is integrated Diff inspected, write ownership respected, returned artifacts verified locally. Fail if relying only on child-agent self-report.
Run is auditable Manifest, trace summaries, decision log, risk log, and closeout report are present. Weak if only chat history contains the rationale.

Minimum Viable Harness

The first implementation should be small enough to use immediately in real repositories. It should not attempt to be a full agent platform.

Version 0.1 deliverables

  • run/TASK.html template for objective, constraints, deliverables, and acceptance object.
  • run/MANIFEST.json schema for artifacts, owners, evidence, checks, and status.
  • harness/CIPH.md natural-language harness with stages, roles, contracts, and stop rules.
  • scripts/verify_manifest.py to fail when required artifacts or evidence pointers are missing.
  • scripts/closeout_check.py to print the prompt-to-artifact checklist before completion.

Deferred intentionally

  • No custom agent runtime until file-backed contracts prove useful in manual operation.
  • No automatic benchmark optimizer until enough real project traces exist.
  • No hidden memory service; all durable state starts as files under the run workspace.
  • No broad multi-agent spawning by default; delegation remains contract-triggered.
  • No completion based only on tests; tests must map to objective requirements.
